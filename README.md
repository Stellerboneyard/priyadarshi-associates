# Priyadarshi & Associates — Website Audit

**Site:** https://stellerboneyard.github.io/priyadarshi-associates/
**Repo:** `stellerboneyard/priyadarshi-associates` (GitHub Pages)
**Reviewed:** index.html (~4,900 lines, single file), README.md
**Date:** August 24, 2026

---

## 1. Architecture

| Layer | What's actually there |
|---|---|
| **Frontend** | One static `index.html` (~361 KB) — HTML, CSS, and vanilla JS all inline. No build step, no framework, no bundler. Client-side routing (`nav()`) fakes a multi-page SPA feel on a single file. |
| **Backend** | **None.** No server code, no API routes, no database, no `fetch()`/`XMLHttpRequest`/`axios` calls anywhere in the file. |
| **Hosting** | GitHub Pages (static hosting only — HTTPS is provided automatically by GitHub, which is good). |
| **"Security layer"** | There isn't one, because there's no backend or data store to secure. All protection needed here is client-side hygiene (XSS, tabnabbing, etc.), not auth/infra security. |

**This is the single biggest thing to understand:** every interactive-looking element — contact form, quick enquiry, booking flow, career application, newsletter signup, live chat — is a **frontend illusion**. None of it sends data anywhere.

## 2. The core issue: forms don't actually submit anything

I checked every "submit" handler in the code (`submitContact`, `heroEnquiry`, `submitApply`, `subscribeNewsletter`, the booking modal, the live-chat widget). They all follow the same pattern:

```js
function submitContact(btn) {
  var fname = document.getElementById('cf-fname').value.trim();
  var phone = document.getElementById('cf-phone').value.trim();
  if (!fname || !phone) { showToast('⚠️ Please fill in your name and phone number.'); return; }
  btn.textContent = '✓ Message Sent! We\'ll be in touch within 4 hours.';
  showToast('✅ Your enquiry has been submitted successfully!');
  // ...nothing is sent anywhere. The value is just discarded.
}
```

There are **zero `<form>` tags** and **zero network calls** in the whole file. A real visitor who fills in the contact form, quick enquiry, appointment booking, career application, or newsletter box sees a convincing "✓ Sent!" confirmation — and the data disappears. For a CA firm whose entire funnel is "get a lead → call them back," **every single lead generated by this site today is being silently lost.** This isn't a security bug, but it's the most urgent issue on the site.

**Fix options (pick one):**
- Wire the forms to a form backend (Formspree, Web3Forms, Getform, or a simple serverless function) that emails/Slacks the firm.
- Add a lightweight backend (e.g., a small Express/Node or Cloudflare Worker endpoint) that stores leads and notifies the team.
- At minimum, route every "submit" through the existing WhatsApp deep link (`wa.me/...?text=`) pre-filled with the form data, so nothing is lost even without a backend.

## 3. Security review

Since there's no backend, most classic risks (SQLi, auth bypass, server misconfig) don't apply. The relevant surface is purely client-side:

| Issue | Severity | Detail |
|---|---|---|
| **`innerHTML` used for chat widget input** | Low (currently mitigated) | The live-chat widget inserts user-typed text via `innerHTML`, but it does pass through an `escapeHtml()` helper first (escapes `&`, `<`, `>`). This is correctly done — good catch by whoever wrote it — but it's easy to accidentally bypass in future edits since several *other* `innerHTML` calls (calculator results, service listings) don't sanitize because they're built from static/internal data only. **Any new field that echoes raw user input into `innerHTML` must go through `escapeHtml()` too**, or better, use `textContent` where no HTML is needed. |
| **`target="_blank"` without `rel="noopener"`** | Low | About 8 links (mobile CTA bar, hero WhatsApp buttons, service-page WhatsApp CTAs) open in a new tab without `rel="noopener noreferrer"`. This is a reverse-tabnabbing risk — the opened page can access `window.opener` and redirect the original tab. Cheap fix: add `rel="noopener"` to every `target="_blank"` link. |
| **No CSRF/auth surface** | N/A | There's no login, no session, no server state to attack — so this category is moot for now. It *will* matter the moment a real backend/admin panel is added. |
| **No CAPTCHA / rate limiting on "forms"** | Low (today) / Medium (once wired up) | Irrelevant while forms don't submit anywhere. The moment you wire them to a real backend, add basic spam protection (honeypot field or a CAPTCHA) or the firm's inbox will fill with bot submissions. |
| **Google Maps embed** | Info only | The embed reveals the exact office pin — intentional and fine for a business site. |
| **No Content-Security-Policy / security headers** | Low | GitHub Pages doesn't let you set custom HTTP headers, so there's no CSP, X-Frame-Options, etc. Not exploitable today (no user data flows anywhere) but worth knowing if this migrates to a host that supports headers. |
| **Client-side `localStorage` use** | Info only | Only used to remember the cookie-consent choice (`cookieChoice`). No PII stored, no issue. |
| **No secrets/API keys in source** | ✅ Good | Checked for API keys, tokens, passwords — none hardcoded. |

**Overall security verdict:** the code itself is clean of classic injection bugs (proper escaping where user input touches the DOM, no `eval`, no hardcoded secrets). The real risk isn't attack surface — it's that **there's nothing behind the site to attack, but visitors don't know that.**

## 4. Trust / compliance issues (matters a lot for a CA firm)

Because this is a regulated-profession website (Chartered Accountants, ICAI-governed), some of the "polish" content is a bigger problem than a normal business site:

- **Placeholder regulatory data displayed as real:** ICAI Firm Reg. No. shows `000000C` and GSTIN shows `10XXXXX1234Z1` — both are obviously fake placeholders, but they're live on the public site. If a prospective client checks these, it will look fraudulent or unfinished rather than trustworthy. **Must be replaced with the real registration number before this goes live for real**, or removed until it can be.
- **Fabricated social proof:** the "Live Activity" feed ("Rajesh Traders filed GST returns 2 hrs ago", "Ananya Singh completed ITR filing 4 hrs ago") and named client testimonials/reviews are hardcoded fictional entries, not real data. Presenting fabricated client activity/testimonials as real is a genuine ethical and potentially legal risk for a licensed CA firm (ICAI has advertising/solicitation restrictions, and fake testimonials can run afoul of consumer-protection rules in India). Recommend flagging this clearly to the client before launch.
- **Broken stat counters:** "0+ Happy Clients / 0+ Years Experience / ₹0Cr+ Tax Savings" show `0+` in the static HTML and are supposed to animate up via `animateCounters()` on scroll — but if JS hasn't loaded yet, hasn't fired (e.g., is below the fold and IntersectionObserver hasn't triggered), or fails silently, visitors see literal "0+" stats, which looks broken/unprofessional.
- **Privacy Policy link in cookie banner points to `#`:** the cookie consent banner links to `[Privacy Policy](#)` instead of the actual Privacy Policy page — ironic, since the site *does* have a real Privacy Policy page elsewhere. Easy fix, but worth catching since GDPR/India's DPDP-style cookie banners are supposed to link to the real policy.
- **Disclaimer/Privacy Policy pages are solid**, actually — well-written and appropriately scoped ("no client relationship is created by an enquiry," calculator disclaimers, data retention terms). No issues there.

## 5. Recommended priority order

1. **Wire up the forms** (contact, quick enquiry, booking, career applications, newsletter) to an actual destination — even a simple WhatsApp-prefill fallback is better than silently discarding leads. *(Business-critical, not just security.)*
2. **Replace placeholder ICAI Reg. No. and GSTIN** with real values, or hide them until available.
3. **Decide what to do about the fabricated "Live Activity" feed and testimonials** — swap for real (anonymized, if needed) data or clearly label as illustrative.
4. Add `rel="noopener"` to the remaining `target="_blank"` links.
5. Fix the cookie-banner Privacy Policy link.
6. If/when you add a real backend for the forms, add basic spam protection (honeypot or CAPTCHA) from day one.

Everything else — code cleanliness, escaping, no secrets in source, HTTPS via GitHub Pages — is in solid shape.
